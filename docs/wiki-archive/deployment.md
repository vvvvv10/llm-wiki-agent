# 大模型部署与服务化

## 推理引擎与部署形态
常见部署是 vLLM、TensorRT-LLM、SGLang、llama.cpp 等推理引擎搭配 GPU 集群，形态有自建（裸金属/K8s）、云厂商托管 API 与 Serverless。选型需权衡可控性、成本与运维复杂度。

## 吞吐与延迟指标
大模型部署需要关注哪些指标：
- 吞吐：每秒处理的请求数（QPS）与每秒生成 Token 数（tokens/s），GPU 利用率。
- 首 Token 延迟 TTFT（Time To First Token）：用户感知的“响应快慢”，受排队与预填充影响。
- 每 Token 时延 TPOT / ITL：生成流畅度。
- 端到端延迟、并发数、错误率与超时率。
交互式场景重 TTFT 与 TPOT，离线批处理重总吞吐与成本。

## 并发与限流
用 Continuous Batching 提升 GPU 利用率，配合请求队列、优先级与公平调度；对外按租户/用户做并发数与 QPS 限流、令牌桶与背压，防止长请求饿死短请求，并设置超时与降级到小模型的兜底方案。

## 量化
量化把权重/激活从 FP16 降到 INT8、FP8、INT4（GPTQ、AWQ、GGUF），显存占用与成本大幅下降、吞吐提升，但有精度损失，必须在回归测试集上验证，优先对激活与 KV Cache 量化。

## 缓存
两级缓存：语义缓存对语义等价的问题直接复用历史答案（需相似度阈值与失效策略）；KV Cache 复用前缀计算，系统 Prompt 等共享前缀可显著降低 TTFT 与成本。

## 可观测性与成本控制
指标包括请求量、TTFT、TPOT、tokens/s、GPU 显存与利用率、错误率、缓存命中率；日志记录 traceID、Token 用量与模型版本，配合链路追踪与告警。成本控制靠模型分级路由（简单任务用小模型）、Prompt 压缩、批处理与缓存，以及按 Token 预算的配额管理。
